## 2. 「AI订阅服务」商城设计

### 2.1 商品是什么
卖两类：
- **代充**：买家拿自己的号，我方给他账户充值/开会员。
- **成品号**：我方注册好、充好值的账号，整号打包卖给买家。

覆盖 GPT / Claude / Gemini 各会员版本。**第一个商品固定 = "GPT Plus 代充"**。其后可有 Pro 5x、Pro 20x 及各类账号。

### 2.2 商品字段（后台可编辑）
每个商品：
- 名称、**图片**、**商品说明**、**价格**（后台设）
- 类型：`代充` / `成品号`
- 平台：`gpt` / `claude` / `gemini`（可扩展）
- 交付方式：`self_service_plus`（仅 GPT Plus 走卡密自助）/ `manual_qr`（其他全部走收款码+人工）
- 排序、上下架状态

### 2.3 两种交付路径

**路径 A —— GPT Plus 代充（唯一自助）**
1. 买家在线付款成功
2. 系统从后台**卡密库**自动发放**一张卡密**给买家 + 一个 **Plus充值链接**（panghu 另做的 Plus 充值网页工具）
3. 客户端用**内置浏览器**打开该链接
4. 走"卡密链路"（详见 §3）完成激活/充值

**路径 B —— 其他所有商品（Pro 5x/20x、成品号、号码类等，人工）**
1. 商品页显示**收款码**（在线支付，价格取后台设置）
2. 买家在线付款
3. 付款成功 → 弹窗提示"**加客服微信**"（附二维码/微信号）
4. 由人工当面/私下给买家充值或交付成品号
5. 客户端只负责"卖"，不做自助充值

> **待确认①**：路径 B 的"在线付款"是走支付宝（像工具订单那样自动到账回调），还是就是一张静态收款码 + 人工核对到账？前者能自动弹"加客服微信"，后者要人工确认。
> **待确认②**：成品号（整号打包卖）付款后怎么交付账号密码给买家？也走卡密？还是人工发？还是客户端里直接展示一次？

## 3. 卡密链路详细设计（★防刷重点）

> **重大更新（2026-07-07 查证）**：Plus 充值工具已存在于 `codex/Plus session.脚本工具`，
> 且**卡密契约、状态机、激活自动化都已做完并本地测试 19/19 通过**。工具本身**不碰支付**，
> 收款/验签/发卡密都在胖虎侧。它自带 `licenseServer.js` 卡密库存服务（校验/锁定/核销/复核接口）。
> **所以卡密链路不用我方从零发明，直接对齐它的契约即可。** 见该仓 `INTEGRATION.md §3`。
>
> **工具已定义的卡密契约（权威）**：
> - 状态机：`issued`（已发放未用）→ `redeeming`（工具已锁定）→ `used`（充值成功核销）；失败→`refund_review`。**与本方案原设计一致。**
> - 工具调用胖虎侧 3 个接口（Bearer 令牌）：① `POST /api/activation-codes/redeem`（校验并锁定，返回 activationId）② `POST /api/activation-codes/{activationId}/used`（核销）③ `POST /api/activation-codes/{activationId}/refund-review`（转人工，不核销）。
> - 胖虎付费成功后写卡密：`POST /api/admin/activation-codes/import`（管理员令牌）。卡密 ≥ 8 位。
> - 买家免手输进入：内置浏览器打开 `http://<工具域名>/?code=<卡密>` 自动填入并激活。
> - 买家在工具里提交自己的 ChatGPT session → 工具自动升级 Plus、关续费、换卡删卡 → 成功后调 ② 核销。
>
> **两种对接方式（推荐 A）**：
> - **方式 A（推荐，最省事）**：胖虎直接部署工具自带的 `licenseServer.js` 当卡密库存服务（指到 `license.aitokenapi.cc`），付费成功后调 import 写卡密即可，零改造。
> - 方式 B：panghu-admin 自己实现同款 redeem/used/refund-review/import 接口。改造量大，不推荐。
>
> **胖虎侧还需做的三件事**（工具 INTEGRATION §0 的诚实清单）：① 卡密库存服务对接（走方式 A 即部署 licenseServer）；② 工具 + 库存服务公网部署；③ 真实 ChatGPT 账号自动化实测（首次大概率要微调页面选择器）。

### 3.1 卡密定位（与工具契约一致）
卡密 = **一次性访问凭证 + 核销凭证**。后台预先录入一批；买家付款后系统自动发一张。**只要充值成功过一次即作废**，作废后既不能再进激活工具、也不能再充。

### 3.2 卡密状态机
```
[库存 in_stock]  --买家付款自动发放-->  [已发放 issued]
[已发放 issued]  --充值成功(核销)-->     [已核销 redeemed / 作废]
[已发放 issued]  --充值失败-->           [仍为 已发放]（允许重试）
[任意]          --后台手动作废-->        [已作废 revoked]
```
关键：**只有"充值成功"才把卡密置为已核销/作废；充值失败不作废，允许重试。**

### 3.3 三道关卡（都必须校验状态）
1. **访问校验关**（内置浏览器第一页输卡密）：校验卡密真实性 + 状态必须是 `issued`。是 → 放行进激活工具；是 `redeemed/revoked` → 拒绝（"卡密已使用/失效"）。
2. **激活工具关**（激活界面再输一次卡密 + 输入 session）：同样要求状态 `issued` 才允许发起充值。
3. **核销关**（充值成功时）：**行锁 + 状态判定 + 幂等**——锁定该卡密行，确认仍是 `issued`，执行充值，成功后在**同一事务**内置为 `redeemed`。并发双充由行锁串行化，第二个请求看到 `redeemed` 直接拒绝。

### 3.4 防刷硬约束（必须写死，不能有例外）
- 卡密核销是**单向不可逆**转移（issued→redeemed），DB 层加唯一约束/行锁保证。
- 访问关与激活关都**拒绝非 issued** 状态，旧卡密无法二次进入。
- "充值成功"事件必须**幂等**：同一卡密的成功核销只发生一次，重复回调/重复点击不重复充值。
- 卡密与**买家身份 + 订单**绑定：发放时记录 `buyer_user_id` / `order_id`，校验时可选校验归属（防卡密被转手盗用）。
- 卡密明文**不入日志**。

> **待确认③**：卡密要不要绑定买家账号（同一卡密只有本人能用）？绑定更安全但买家换设备/换号会受限。
