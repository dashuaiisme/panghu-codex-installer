## 1. 登录 bug 修复历程（避免你重复踩坑）

现象：客户端登录页点"登录胖虎AI客户端"按钮 → 最初完全无反应，修复后变成界面卡死"未响应"，再修后用户仍反馈无反应。三层根因：

1. **前端缺函数**：`src/ui/index.html` 按钮 `onclick="submitLogin()"`，但 `submitLogin` 从未定义（Codex 遗留）。→ 已补 `submitLogin()`（读 loginUser/loginPass + rememberPwd/autoLogin 勾选，调 `pywebview.api.login`）。
2. **同步网络请求卡死 GUI**：`WebviewApi.login` 原本同步执行 `login_panghuai`（20s 网络请求）阻塞 WebView 线程。→ 已改为后台线程 `_login_bridge_worker`，`login()` 只启线程立即返回 `{success:true, pending:true}`。
3. **js_api 回调内同步 evaluate_js 可能重入死锁**：已把所有 `self.app.log`/`evaluate_js` 移进后台线程，`login()` handler 内不碰 evaluate_js。
4. **登录页看不到反馈**：进度/错误原走 `appendPythonLog`，写到登录后才可见的日志区，登录页挡住了 → 用户看着"没反应"。→ 已在登录按钮上方加 `#loginStatus` 状态条 + `window.setLoginStatus`/`window.showToast`；后台线程通过新增的 `PanghuInstaller.push_webview_toast`（约 9357 行）回推结果。

**当前代码期望行为**：点登录 → 立即显示黄色"正在登录…" → 成功切进配置流程 / 失败显示红色具体原因（"登录失败：账号或密码错误" / "登录接口连接失败"）。

**如果真机测试仍无反应，重点排查方向**（按可能性）：
- pywebview 的 `evaluate_js` 从后台线程调用在当前 backend（Windows EdgeChromium）是否可靠——若不可靠，改用 `window.evaluate_js` 需在主线程 marshaling，或改为前端轮询一个状态方法。
- `push_webview_toast` 里 `evaluate_js("(window.showToast||window.appendPythonLog)(...)")` 是否真的执行——可在 F12 devtools（若 pywebview 开了 debug）看控制台。
- 确认客户端确实加载的是最新 `index.html`（pywebview 可能缓存；`run-windows.bat` 重启即可）。
- 兜底方案：如果 pywebview 的 GUI 线程回调机制太脆，把登录结果做成"前端每 500ms 调一次 `get_login_status()` bridge 拉状态"的轮询模型，彻底避开从 Python 主动 push。

登录后端链路本身是好的：`login_panghuai`（POST `https://aitokenapi.cc/api/user/login?turnstile=`）→ `activate_deployer`（POST `/api/deployer/activate`）→ 存会话 → `sync_webview_state()` 切界面。见 `src/panghu_ai_client.py` 2130、2159 行。注意登录 URL 末尾 `turnstile=` 是空的，若服务端强制人机验证可能是隐患，但也可能服务端给客户端开了免验证——真机看服务端返回的 message 即可确认。
